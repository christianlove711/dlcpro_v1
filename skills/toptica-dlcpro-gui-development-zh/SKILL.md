# TOPTICA DLC pro 自定义界面开发

目标是基于 `PySide6` 与 TOPTICA 官方 Python SDK 开发一套自定义 DLC pro 控制软件，用 Python 实现对 DLC pro 各项功能的完整控制，而不是只替代官方软件中的某一个页面。

开始前先阅读 [source-map.md](references/source-map.md)，确认 SDK 与手册在当前仓库中的位置。

## 开发目标

- 使用官方 SDK 连接并控制 DLC pro
- 使用 PySide6 构建自定义图形界面
- 界面同时提供中文与英文
- 依据 `Manual.md` 理解设备行为、安全限制、接线和操作流程
- 逐步实现对 DLC pro 各项控制功能的 Python 化实现

## 资料优先级

按以下顺序查证：

1. 官方 SDK 文档与官方示例
2. 官方设备手册 `Manual.md`
3. 项目现有代码
4. 常识性推断

只有当前三者都没有明确说明时，才允许做最小化推断，并且必须明确说明“这是推断，不是官方结论”。

## 开发流程

每次实现功能时按以下顺序执行：

1. 明确功能目标。
   例如：连接设备、读取电流、切换发射、控制扫描、显示状态、绘图记录、替代官方某个页面。
2. 先查 SDK，确认该功能是否有官方接口以及正确调用方式。
3. 再查 `Manual.md`，确认该功能对应的设备行为、限制和安全要求。
4. 最后查看项目现有实现，决定如何接入当前代码结构。
5. 如果官方资料与现有代码冲突，先指出冲突，再按官方资料修正实现。
6. 完成后说明该实现依据来自 SDK、手册，或项目本地结构。

在修改界面结构前，先明确一个产品层面的交互前提，并在代码里保持一致：

- 这个功能是放在主窗口的堆叠页里，还是点击后弹出独立 `QMainWindow`？
- 这次任务是新增功能、调整视觉样式，还是两者同时进行？
- 用户说“和主界面风格一致”时，指的是只统一配色控件，还是连外层容器、边距、标题层级也要一致？

除非用户明确要求，否则不要擅自把“弹窗窗口”改成“主界面切页”，也不要反过来改。

## 连接模块要求

- 开发连接模块时，明确区分串口连接与网络连接两条路径。
- 串口通信依赖 `pyserial`，相关实现、异常处理、端口选择和连接失败提示都要考虑进去。
- 网络连接依赖 `ifaddr`，相关实现要考虑本机网络接口发现、地址选择和网络可达性判断。
- 连接模块设计时，不要把串口和网络逻辑硬编码在界面层，优先做成独立的 connection/service 层。
- 若 SDK 对底层连接有既定包装方式，优先遵循 SDK 的连接模型，不要自行绕开 SDK 直接控制设备协议。

## 硬规则

- 不要发明不存在的 API、参数名、命令名、返回字段或状态名。
- 不要假设单位、范围、默认值、枚举值或时序行为。
- 不要因为项目里已经写了某个参数名，就默认它是正确的。
- 如果 SDK 与项目现有实现冲突，必须指出冲突并优先遵循 SDK。
- 如果手册与 SDK 分工不同：编程接口以 SDK 为准，设备行为、安全、接线、操作流程以手册为准。
- 如果官方资料没有明确写出某个行为，要明确标注“官方资料未确认”。
- 涉及激光发射、联锁、高压、模块接线、上电/断电等内容时，优先查手册再实现。

## PySide6 实现要求

- 将设备通信逻辑与界面逻辑分离。
- 优先把 DLC pro 控制封装在 controller/service 层，不要把 SDK 调用直接散落在界面控件里。
- 所有面向用户的界面文本、按钮、提示、状态描述都要支持中文和英文。
- 双语支持应在架构层面预留，不要把中英文文本硬编码在业务逻辑里。
- 界面控件状态应与设备实时状态对应，避免只改界面不改设备，或设备已变更但界面未刷新。
- 对长耗时操作、轮询、连接重试和状态刷新，考虑使用合适的线程、定时器或异步机制，避免阻塞界面。
- 错误提示要区分“连接失败”“参数不存在”“设备拒绝”“安全限制”等不同原因。
- 如果界面存在后台轮询，必须避免“设备断开后每次轮询都弹一次模态错误框”这种体验。对轮询链路的掉线错误，应只提示一次，并及时停掉轮询或重置为未连接状态。
- 如果这是面向桌面操作员使用的独立程序，主窗口关闭时优先补一个明确的退出确认框。
- 当某个弹窗页面持续变大时，优先先把页面壳拆到 `windows/`，再把 `CC`、`TC`、`PC` 这类功能块拆成独立 `QWidget` 面板放到 `widgets/`。
- `controllers/` 层不是为了好看才加，只有当逻辑已经出现跨控件协同、多步写入、轮询联动、状态机或跨模块流程时，才值得引入并实际承接这些流程。
- 对会在多个模块反复出现的 UI 模式，应尽早抽成复用控件，不要复制粘贴。典型对象包括：开关按钮、步进按钮行、带“当前调节”按钮的数值输入行。
- 对非显然的结构协作规则，优先补简短中文注释，解释“为什么这样拆”或“这个约束在保护什么”，不要写成重复代码字面的流水账。

## 弹出窗口实现补充

- 如果 `Laser`、`Scan&Lock`、`Relock`、`Stabilization` 这类页面的目标是点击后弹出独立 `QMainWindow`，要保留这个交互模型，不要默认改成主界面内部切页。
- “和主界面风格一致”不能只理解成内部面板颜色相同，还要检查外层骨架是否一致：外边距、分组容器、标题层级、间距节奏、边框可见性。
- 注意样式是否只绑定在主窗口实例上。若使用 `self.setStyleSheet(...)` 只给主窗口加样式，独立弹出的 `QMainWindow` 往往不会自动继承，需要改为应用级样式或显式给弹窗设置样式。
- 对弹窗按钮行为，不只检查 `show()`，还要确认窗口是否被 `raise_()`、`activateWindow()` 拉到前面，避免用户误以为“点击无反应”。

## 双语界面补充

- 每次改动某个页面后，要把该页面所有可见文本整体检查一遍，不要只更新新增控件的文案。
- 除非用户明确要求，否则不要出现“英文标题 + 中文字段名”这类混搭界面。
- `CC`、`TC`、`ARC`、物理单位、已验证的产品缩写可以保留，但描述性文本应在当前语言模式下保持整体一致。
- 中文模式优先使用自然中文表达；英文模式使用完整自然英文，不要残留零碎的另一种语言。

## 样式陷阱

- 小心使用 `QWidget { background: ... }` 这类过宽的全局选择器，它可能让普通文本标签也带上一层深色底，尤其在弹窗和嵌套面板里会显得很丑。
- 如果某些静态文字应当直接贴在面板上展示，要显式检查 `QLabel` 是否应设置为 `background: transparent`。
- 只有真正需要强调的控件才保留底色，比如状态徽标、只读数值框、需要边框包裹的读回值。

## 实时交互与轮询

- 不要因为某个数值框可编辑，就默认每次写入都弹确认框。确认框应保留给安全相关动作、硬件上限、风险较高的大步长修改，或用户明确要求确认的写入。
- 像设定温度、设定压电电压、斜率限制、扫描频率/幅度这类普通设定值，默认应允许用户直接通过 `spinbox` 上下键调整，而不是每改一次都弹模态框。
- 如果程序存在后台轮询，不要在渲染时无条件覆盖用户正在操作的控件。数值框当前有焦点时，应暂缓把读回值写回该框；下拉框当前有焦点或下拉列表正展开时，应暂缓同步 `currentIndex`。
- 轮询刷新和真实写入不是同一类“忙碌”。后台 poll 不应像写设备那样冻结整页控件，更不应打断用户正在思考和选择的下拉项。
- 如果弹窗页面是可滚动的，刷新或写入前后要保留滚动位置。用户正在调某个参数时，界面不应因为一次刷新就突然跳到页面顶部或底部。
- 如果自动写入逻辑通过定时器延后触发，而后台轮询和写入共用同一执行通道，要避免“轮询占用中导致待写入值被悄悄吞掉”。更稳妥的做法是：当执行器正忙时，重新挂起定时器，等当前任务结束后再尝试写入。

## 数值步进交互

- 对 `CC`、`TC`、`PC` 这类模块，优先采用“每个模块一排步进按钮”的方案，不要给每个数值项都复制一整排步进控件。
- 不要只依赖“当前焦点”来决定步进控制目标；如果用户肉眼看不出来当前绑定了哪个输入框，这个交互就不够稳。
- 更推荐的模式是：模块里保留一排公共步进按钮，同时在每个可编辑数值框右侧放一个显式的“当前调节”按钮。
- “当前调节”按钮必须有清晰的选中态反馈，让用户一眼就知道这排步进现在控制的是哪个参数。
- 每个模块应有一个稳定的默认目标，但用户应能通过点击右侧按钮，快速把该模块的步进控制切换到另一个参数上。

## 可扩展结构

- 如果一个弹窗窗口的布局代码已经膨胀到几百行，应把它视为拆分信号，而不是继续把新模块塞进同一个文件。
- 推荐的拆分顺序是：
  1. `app.py` 只保留全局外壳、导航、连接区和任务调度
  2. `windows/` 负责弹窗窗口外壳和页面拼装
  3. `widgets/` 负责复用控件和功能面板，例如 `CcPanel`、`TcPanel`、`PcPanel`
  4. `controllers/` 在确有需要时承接业务流程、渲染协调和多步行为
- 做结构重构时，优先保持用户现有交互不变，再改善内部组织；除非用户明确要求，不要把“文件搬家”和“交互重做”混在一次改动里。

## 功能实现策略

目标不是复刻官方软件中的单个页面，而是用 Python 逐步实现 DLC pro 的完整控制能力。优先按模块推进：

1. 设备连接与识别
2. 基础状态显示
3. 核心参数读写
4. 发射控制与安全相关状态
5. 电流、温度、压电、扫描等主要控制页
6. 曲线显示、记录、告警
7. 继续补齐其余控制功能，直到主要设备能力都能通过 Python 与自定义 GUI 完成操作

如果某项设备能力希望实现，但 SDK 中找不到可用接口，不要硬编功能，应该明确标记为“当前未在已确认 SDK 接口中找到依据”。

## 输出要求

- 在说明或代码注释中，尽量标注依据来自 `SDK` 还是 `Manual`。
- 当实现依赖某条非显然规则时，给出对应文档路径或章节线索。
- 审查代码时，优先指出“与官方资料不一致”的问题，而不是只看代码风格。
- 涉及连接模块时，说明该实现依赖 `pyserial` 还是 `ifaddr`，以及依据来自 SDK 还是项目层封装。
- 如果一开始界面交互模型存在歧义，在最终说明中要明确写出实际采用的是“独立弹窗”还是“主界面切页”。
